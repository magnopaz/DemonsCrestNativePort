# Save state -> extracted room mapping

Generated by `tools/oracle/map_saves_to_areas.py`; the machine-readable form
is `captures/save_to_area.json`:

```json
{"save": "...", "raw_id": 74, "area": 37, "score": 1.0,
 "method": "stage_id+bg1", "verified": "screen-unique",
 "tied_areas": [37], "screen": [1, 153], "screen_areas": [37],
 "object_species": [30], "object_overlap": 1, "object_unique": true,
 "canonical_area": 37}
```

## Result

- **219/219 save states mapped** to `room_area<N>.json`, covering **54 distinct areas**.
- **114** verified by a 32x32 BG screen that exists in *exactly one* area.
- **71** verified up to a byte-identical ROM duplicate class (the same room is reachable as several table entries).
- **34** carry the loader id only (menus, overworld map, boss arenas, where BG1/BG2 is not a room tilemap).
- **0 conflicts**: no save where a whole matched screen belongs to a different area than the loader id.

BG1 score: 103 exact (1.000), 82 partial (0.60-0.99), 34 none (<0.60).

Independent third signal - the live object pool (`$1080`, 26 slots) against the
ROM object list of the mapped area (`$81:C874`):

- **126/126** saves with live objects share at least one species with the mapped area;
- **61** are a *unique* best match; no save is better explained by any other area's object list.

## Why `area = WRAM $008D / 2`

The room loader reads the area pointer table with an indexed load,
`LDA $81:A291,Y`, and the guest keeps that `Y` in `$008D`. Table entries are
2 bytes, so `$008D` is the **byte offset**, not the entry number:

```
area = $008D / 2
```

Evidence:

- all 54 distinct `$008D` values across the save set are **even** (0, 2, 4, ... 192 -> areas 0..96);
- dividing by two reproduces every room BG1 can identify, including the old "counter-example" cemetery (`2 -> 1`);
- the values previously read as area numbers are exactly 2x the real areas: `save7 48 -> 24`, `save8 74 -> 37`, `save9 58 -> 29`.

## How the BG1 check works (`tools/oracle/room_match.py`)

The guest builds BG1/BG2 from the same `$8F+set` superblock tables the extractor
uses, so a live 64x32 VRAM window contains whole 32x32 ROM screens. Two details
make the match exact:

1. the screen table has **256** entries (`$8F+set:$8000 + screen*128`), not 128 -
   most late-game rooms use screen ids above 127, which the older matcher
   silently skipped (areas 24, 37, 46, 10 and 4 were all unmatchable because of it);
2. the guest rewrites the **priority (bit 13) and flip (bits 14/15)** bits of the BG
   words when it loads a room, so words are compared with `mask 0x1FFF` (tile +
   palette). Without the mask only rooms whose block table already carried the
   same flags matched.

Matching is a row-vote torus scan over every 32x32 window of the live buffer, so a
screen boundary that falls inside the window (the guest rewrites columns while the
camera scrolls) still scores: 32/32 rows means the window is that screen cell for
cell. Blank/filler screens are excluded so they cannot win a tie.

## ROM-duplicate classes

Areas that share **both** the info block (`$81:A291`) and the grid block
(`$81:A6D8`) are byte-identical rooms: no content signal can separate them. The
mapper reports the class in `screen_areas` and picks the lowest id as
`canonical_area`; the loader id picks the entry the game actually used.

## Caveats

- The `loader-only` rows are menus (`menu_cutscene`, `map_*`), the overworld and
  boss arenas. `$008D` still holds a plausible id there, but nothing verifies it;
  treat those as "loader id, unverified".
- `$008D` is read after the save settles (40 frames past the first lit frame,
  three sampled frames at +10/+25/+45).
- Probe dumps live in `captures/rooms/<save stem>/` (`f<frame>.json`,
  `f<frame>.vram.bin`, `wram.bin`, `cgram.bin`, `ppu.json`, `meta.json`).
- `captures/room_matches.json` caches the per-save match ranking so re-running the
  mapper is seconds instead of minutes (`--use-cache`).

## Forcing an arbitrary area (no save state needed)

`tools/oracle/load_area.py --area N` makes the guest load area `N` on demand and
captures it into `captures/area<N>/` (`fNNNNNN.json` + `fNNNNNN.vram.bin`, the
same format `capture_area_frame.py` writes). 64 of the 113 rooms had no
capture directory (49 did, from the 219 save states); this is how the rest are
captured without owning a save for the room.

`$008D` is not a load switch (trap 22), because only the *room-load task* reads
it. That task is id 4 (`$80:B71A`), and the game only starts it from its own
transition code - which is also the only writer of `$008D` during a screen
change:

```
80:BB58  lda $008D      ; current area, byte offset into $81:A291
80:BB69  sta $0E56      ; remember the room being left
80:BB6C  lsr / tax
80:BB6E  lda $97DA,X    ; sequential "next area" table
80:BB75  sta $008D      ; <-- the only writer during a transition
80:BB7F  jmp $BAB7      ; $BAB7: lda #4 / jmp $829B -> current task = id 4
```

`$829B` writes the id into the task slot and re-dispatches it through
`jmp ($82C3,X)`; the ids are **byte offsets**, so id 4 selects table entry 2 =
`$80:B71A`. The loader reads `$008D` for music at entry but does not consume it
for the room build until after the fade-out, so overwriting `$008D` in the
window between the transition starting and the build retargets the load:

1. resume a save that stands in front of a door and hold the walk button until
   `$008D` changes (the cemetery right door is the default; several others are
   tried in turn);
2. write `$008D = 2*N` every frame for ~30 frames;
3. sample the frames after the build and keep the one whose live BG1 matches
   `room_area<N>.json` at >= 0.9, then delete the other frames.

pair plus `capture.json` and `capture.log`.

Areas that do not verify are reported, not silently written: the tool prints
`not verified: best areas by BG1 = [...]`. Observed failure modes:

- **right room, nothing to match** - the room is mostly empty where the camera
  lands (61, 76: their ROM BG1 is 25% non-zero) or the guest has only partly
  rewritten the VRAM ring (wide rooms 68/71, which score 0.56/0.63 = the half
  of the window that is one screen);
- **build did not run** - 72/74 leave VRAM blank although `$008D` holds `2*N`,
  i.e. the loader was started but never uploaded; 51/99-on-the-first-run left
  the display blanked. Re-running 99 with the sampling window widened fixed it,
  so at least part of this class is "the build lands later than the old sample
  window", not a hard failure.


### Limits

- The player is placed at the *target* room's spawn point - the spawn comes
  from the room data, not from the door that was used - so for rooms entered
  from a different side it can land in mid-air. The room still builds and the
  capture is valid, but it can fade to black right after; `capture.json`'s
  `visible` records whether a lit frame was among the samples.
- Verification is a *content* test, so rooms that are mostly empty where the
  camera lands cannot reach 1.0. Sparse rooms (e.g. 61/76, whose ROM BG1 is 25%
  non-zero) score their best screen row count, and rooms whose VRAM ring is
  only partly rewritten (wide rooms: the guest aligns the ring to the camera)
  score the best half. The tool then prints `not verified: best areas by BG1 =
  [...]` - the areas the frame *does* look like - which is the diagnostic that
  separates "wrong room" from "right room, nothing to match".
- `--walk-chunk 1` polls the transition frame by frame; the default 4 is enough
  for the cemetery door.
